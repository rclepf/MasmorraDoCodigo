Ligação com a UC anterior

Na UC anterior você viu que um bom projeto 3D reaproveita partes: um modelo-base que ganha variações, materiais compartilhados, objetos instanciados. A programação orientada a objetos aplica a mesma ideia ao código: uma classe-base descreve o que todo inimigo tem, e cada monstro acrescenta o que o torna único.

Dica de produção. Slime e esqueleto, no kit, são dois modelos com comportamentos diferentes. Se você criou criaturas no Blender, escolha duas que se comportem de modo distinto, como uma lenta e resistente e outra rápida e frágil.

Os quatro pilares, na prática

PilarIdeiaNo jogo
EncapsulamentoEsconder os dados e expor só o necessárioA vida é privada: só se altera chamando ReceberDano
HerançaUma classe reaproveita outraSlime e Esqueleto herdam de Inimigo
PolimorfismoMesma chamada, comportamento diferenteinimigo.Atacar() faz coisas distintas em cada tipo
AbstraçãoDeclarar o que deve existir sem dizer comoAtacar é obrigatório, mas cada inimigo define o seu

Em C#, abstract marca uma classe (ou método) que não pode ser usada sozinha. virtual permite que filhos substituam um método, e override é a substituição. protected deixa o filho acessar um campo, sem expô-lo ao resto do jogo.

A classe-base

Antes de escrever, responda: o que todo inimigo faz? Todo inimigo tem vida, recebe dano, morre e ataca. A diferença está em como ataca.

Inimigo.cs 
using UnityEngine;

public abstract class Inimigo : MonoBehaviour
{
    [SerializeField] protected int vidaMaxima = 3;
    [SerializeField] protected float velocidade = 2f;

    protected int vidaAtual;

    protected virtual void Awake()
    {
        vidaAtual = vidaMaxima;
    }

    public void ReceberDano(int dano)
    {
        vidaAtual = Mathf.Max(0, vidaAtual - dano);
        if (vidaAtual == 0) Morrer();
    }

    protected virtual void Morrer()
    {
        Destroy(gameObject);
    }

    public abstract void Atacar(Transform alvo);
}

ReceberDano não é virtual de propósito: a regra de que a vida não passa de zero é igual para todos e não deve ser quebrada por um filho.

Dois monstros, uma base

Slime.cs 
using UnityEngine;

public class Slime : Inimigo
{
    [SerializeField] private int danoDeContato = 1;

    public override void Atacar(Transform alvo)
    {
        // O dano real ao jogador chega no módulo 6; por ora, apenas registramos
        Debug.Log($"{name} esmaga {alvo.name} causando {danoDeContato} de dano");
    }
}
Esqueleto.cs 
using UnityEngine;

public class Esqueleto : Inimigo
{
    [SerializeField] private int danoDaEspada = 2;
    [SerializeField] private GameObject chavePrefab;

    public override void Atacar(Transform alvo)
    {
        Debug.Log($"{name} golpeia {alvo.name} com a espada: {danoDaEspada} de dano");
    }

    protected override void Morrer()
    {
        // Esqueletos deixam uma chave ao morrer; depois, o comportamento comum
        if (chavePrefab != null)
            Instantiate(chavePrefab, transform.position, Quaternion.identity);

        base.Morrer();
    }
}

Repare no base.Morrer(): o esqueleto acrescenta um comportamento e depois reaproveita o da classe-base, sem copiar código. Quando você mudar o que acontece ao morrer em Inimigo (som, partículas), todos herdam a mudança.

Polimorfismo em ação

O ganho aparece quando alguém usa o inimigo sem saber qual é o tipo. Este gerenciador controla qualquer monstro:

GerenteDeSala.cs 
using System.Collections.Generic;
using UnityEngine;

public class GerenteDeSala : MonoBehaviour
{
    [SerializeField] private Transform jogador;
    [SerializeField] private List<Inimigo> inimigos = new List<Inimigo>();

    [ContextMenu("Todos atacam")]
    private void TodosAtacam()
    {
        foreach (Inimigo inimigo in inimigos)
        {
            if (inimigo != null) inimigo.Atacar(jogador);
        }
    }
}

Monte uma sala de teste

Crie dois inimigos: um com Slime e outro com Esqueleto, cada um com o modelo do kit (ou o seu). Arraste ambos para a lista inimigos do GerenteDeSala e o Jogador para o campo correspondente.

Dispare pelo menu

Clique com o botão direito no componente GerenteDeSala e escolha Todos atacam. O Console mostra mensagens diferentes para cada tipo, mesmo com a mesma chamada Atacar.

Aperfeiçoe

Crie um terceiro monstro herdando de Inimigo (um morcego, uma aranha, um golem). Quantas linhas do GerenteDeSala você precisou mudar? A resposta certa é zero.

Checkpoint: a lista aceita os três tipos de inimigo, o Console mostra um ataque diferente para cada um e o esqueleto deixa uma chave ao morrer.

Quando a herança atrapalha

Herança funciona bem para "é um": um slime é um inimigo. Mas ela fica rígida quando as combinações crescem. E se você quiser um inimigo que voa e atira, outro que voa e não atira, outro que anda e atira? Criar InimigoVoadorAtirador e InimigoVoadorPacifico multiplica classes.

Esse problema é resolvido no próximo módulo, com composição: em vez de herdar, o objeto recebe componentes (Vida, Voo, Ataque à Distância). A Unity é construída nessa ideia. Domine as duas formas e escolha a certa para cada caso.

Checkpoint do módulo

  • uma classe-base abstrata para os personagens ou objetos adversários do jogo da equipe;
  • pelo menos 3 classes filhas com comportamentos distintos, sendo uma delas sobrescrevendo um método virtual e chamando base;
  • uma classe que usa todos os filhos por meio da classe-base;
  • diagrama de classes atualizado no repositório.

As instruções completas estão na Atividade Prática C05.

Problemas comuns

Erro: não é possível criar instância de classe abstrata

Você tentou usar new Inimigo() ou adicionar Inimigo a um objeto. Classes abstratas só servem de base: adicione o Slime ou o Esqueleto.

Erro: o filho não implementa o membro abstrato

Todo método abstract precisa de um override em cada filho. Confira o nome e os parâmetros.

O Awake do filho substitui o da base e a vida fica em zero

Se o filho declarar o próprio Awake, use protected override void Awake() e chame base.Awake() na primeira linha.

A lista do gerenciador aparece vazia no Inspector

O campo precisa ser [SerializeField] private List<Inimigo> e os objetos arrastados devem ter um componente que herda de Inimigo.
