Ligação com a UC anterior

Na UC anterior, o trabalho terminava quando o material estava pronto para ser entregue: arquivos nomeados, formatos corretos, documentação junto. Aqui o raciocínio é o mesmo, com uma etapa a mais: antes de entregar, você prova que o jogo funciona, e depois empacota tudo para que outra pessoa o execute sem a sua ajuda.

Dica de produção. Entregar é parte do projeto, não um favor no fim. Reserve pelo menos um dia inteiro para testes, build e documentação, e comece pela build: quase todo grupo descobre na véspera que o jogo funciona no Editor e quebra no executável.

Três formas de testar

TipoComoBom para
PlaytestOutra pessoa joga e você observa em silêncioEntender se o jogo é claro, justo e divertido
Teste em modo de edição (EditMode)Código automático, roda sem apertar PlayRegras puras: busca de caminho, validação, save
Teste em modo de jogo (PlayMode)Código automático que roda a cena de verdadeComponentes que precisam de Awake, física e tempo

Os testes automáticos protegem contra a regressão: ao mudar o código na semana da entrega, você descobre em segundos se quebrou o que já funcionava.

Preparando o projeto para testes

O Unity Test Framework já acompanha o projeto (confira em Window > Package Manager; se não aparecer, instale Test Framework). Para que o código de teste enxergue o seu código, ele precisa estar dentro de um assembly definition:

Crie o assembly do jogo

Na pasta Assets/Scripts, botão direito > Create > Scripting > Assembly Definition, com o nome Jogo. No Inspector, em Assembly Definition References, adicione Unity.InputSystem.

Crie as pastas de teste

Em Assets/Tests, use Create > Testing > Test Assembly Folder duas vezes: uma para EditMode e outra para PlayMode. Em cada assembly de teste, adicione Jogo às referências.

Abra o executor

Window > General > Test Runner. As abas EditMode e PlayMode listam os testes e permitem rodar um ou todos.

Testes em modo de edição

Cada teste tem três partes: preparar (arrange), agir (act) e conferir (assert). Estes testes verificam o código dos módulos 8, 10 e 11:

JogoEditModeTests.cs 
using System.IO;
using System.Text.RegularExpressions;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

public class BuscaEmLarguraTests
{
    [Test]
    public void Contorna_o_muro_pelo_caminho_mais_curto()
    {
        var parede = new bool[5, 5];
        for (int y = 0; y < 4; y++) parede[2, y] = true;   // passagem só em y = 4

        var caminho = BuscaEmLargura.Caminho(parede, new Vector2Int(0, 0), new Vector2Int(4, 0));

        Assert.IsNotNull(caminho);
        Assert.AreEqual(13, caminho.Count);
    }

    [Test]
    public void Destino_isolado_devolve_null()
    {
        var parede = new bool[5, 5];
        for (int y = 0; y < 5; y++) parede[2, y] = true;

        Assert.IsNull(BuscaEmLargura.Caminho(parede, new Vector2Int(0, 0), new Vector2Int(4, 0)));
    }
}

public class ValidadorDeSaveTests
{
    [Test]
    public void Limita_pontos_e_vida()
    {
        var d = ValidadorDeSave.Sanear(new DadosSave { pontos = int.MaxValue, vida = -5 });

        Assert.AreEqual(1_000_000, d.pontos);
        Assert.AreEqual(1, d.vida);
    }

    [Test]
    public void Posicao_invalida_volta_para_a_origem()
    {
        var d = ValidadorDeSave.Sanear(new DadosSave { posicao = new Vector3(float.NaN, 0, 0) });

        Assert.AreEqual(Vector3.zero, d.posicao);
    }

    [Test]
    public void Remove_itens_impossiveis()
    {
        var d = new DadosSave();
        d.itens.Add(new ItemSalvo { nome = "Chave", quantidade = 2 });
        d.itens.Add(new ItemSalvo { nome = "Truque", quantidade = 99999 });

        ValidadorDeSave.Sanear(d);

        Assert.AreEqual(1, d.itens.Count);
    }
}

public class SaveTests
{
    private const int Slot = 99;   // slot só para testes, para nunca tocar no save real

    [TearDown]
    public void Limpar()
    {
        SistemaSave.Apagar(Slot);
        string seguro = Path.Combine(Application.persistentDataPath, "seguro.json");
        if (File.Exists(seguro)) File.Delete(seguro);
    }

    [Test]
    public void Salvar_e_carregar_devolve_os_mesmos_dados()
    {
        SistemaSave.Salvar(new DadosSave { pontos = 42, vida = 2, fase = "Cripta" }, Slot);

        DadosSave lido = SistemaSave.Carregar(Slot);

        Assert.AreEqual(42, lido.pontos);
        Assert.AreEqual(2, lido.vida);
        Assert.AreEqual("Cripta", lido.fase);
    }

    [Test]
    public void Arquivo_corrompido_vira_partida_nova()
    {
        File.WriteAllText(Path.Combine(Application.persistentDataPath, $"save{Slot}.json"), "{ isto nao e json");
        LogAssert.Expect(LogType.Warning, new Regex("ileg"));

        DadosSave lido = SistemaSave.Carregar(Slot);

        Assert.AreEqual(0, lido.pontos);
    }

    [Test]
    public void Save_assinado_valido_carrega_e_editado_e_recusado()
    {
        SaveAssinado.Salvar(new DadosSave { pontos = 5 });
        Assert.IsTrue(SaveAssinado.TentarCarregar(out DadosSave ok));
        Assert.AreEqual(5, ok.pontos);

        string arquivo = Path.Combine(Application.persistentDataPath, "seguro.json");
        File.WriteAllText(arquivo, File.ReadAllText(arquivo).Replace("\"pontos\":5", "\"pontos\":9999"));

        Assert.IsFalse(SaveAssinado.TentarCarregar(out _));
    }
}

Dê nomes que contem uma história (Destino_isolado_devolve_null): quando o teste falhar, o nome já diz o que quebrou.

Testes em modo de jogo

Componentes como Vida precisam que a Unity chame Awake, o que só acontece rodando a cena. O teste vira uma corrotina marcada com [UnityTest]: cada yield return null espera um quadro.

JogoPlayModeTests.cs 
using System.Collections;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;

public class VidaTests
{
    private GameObject objeto;

    [SetUp] public void Criar() => objeto = new GameObject("Teste");
    [TearDown] public void Destruir() => Object.Destroy(objeto);

    [UnityTest]
    public IEnumerator Dano_reduz_a_vida_e_nao_passa_de_zero()
    {
        var vida = objeto.AddComponent<Vida>();
        yield return null;                      // deixa o Awake rodar

        vida.ReceberDano(1);
        Assert.AreEqual(vida.Maxima - 1, vida.Atual);

        vida.ReceberDano(999);
        Assert.AreEqual(0, vida.Atual);
    }

    [UnityTest]
    public IEnumerator Cura_nao_passa_do_maximo()
    {
        var vida = objeto.AddComponent<Vida>();
        yield return null;

        vida.ReceberDano(1);
        vida.Curar(50);

        Assert.AreEqual(vida.Maxima, vida.Atual);
    }

    [UnityTest]
    public IEnumerator Segundo_gerente_e_descartado()
    {
        var primeiro = objeto.AddComponent<GerenteDeJogo>();
        yield return null;

        var outro = new GameObject("Outro").AddComponent<GerenteDeJogo>();
        yield return null;

        Assert.IsTrue(outro == null);           // foi destruído pelo Awake
        Assert.AreSame(primeiro, GerenteDeJogo.Instancia);
    }
}
Checkpoint: a aba EditMode mostra todos os testes em verde, a aba PlayMode também, e ao quebrar de propósito uma regra (por exemplo, trocar 13 por 12) o teste correspondente fica vermelho.

Medir antes de otimizar

Otimizar sem medir é adivinhar. Abra o Profiler (Window > Analysis > Profiler), aperte Play e jogue o trecho mais pesado do jogo:

SintomaOnde olharCausas comuns
Quedas de quadros em picosLinha CPU UsageMuitos Instantiate, FindObjectOfType no Update
Travadinhas periódicasColuna GC AllocCriação de objetos a cada quadro (use pool, módulo 9)
Jogo lento em geralAba RenderingMuitos objetos com materiais diferentes, luzes em tempo real demais
Memória altaMemory ProfilerTexturas grandes demais, áudio sem compressão

Meta para a entrega: 60 quadros por segundo estáveis no computador do laboratório. Registre o valor medido, não uma impressão.

Gerando a build

Configure o jogo

Em Edit > Project Settings > Player, preencha nome da empresa e do produto, versão (por exemplo 1.0.0) e ícone.

Liste as cenas

Em File > Build Profiles, na plataforma Windows, confira se todas as cenas do jogo aparecem em Scenes in Build, na ordem certa. Cena fora da lista é o erro de build mais comum.

Gere o executável

Clique em Build e escolha uma pasta vazia fora do projeto. A Unity cria o .exe e uma pasta de dados.

Teste a build, não o Editor

Em outro computador, ou ao menos em outra conta, rode o executável do começo ao fim, incluindo salvar e carregar. Erros que aparecem só aqui costumam ser caminhos, cenas esquecidas ou arquivos que dependiam do Editor.

Compacte

Compacte a pasta inteira em um .zip com o nome NomeDoJogo_v1.0.0_Windows.zip.

Entregando o projeto

Uma entrega completa tem quatro partes, e qualquer pessoa deve conseguir usar cada uma sem perguntar nada:

ParteConteúdoOnde
JogoA build compactadaRelease no GitHub ou página no itch.io
CódigoO projeto Unity limpo, sem as pastas Library, Temp e LogsRepositório Git com .gitignore de Unity
Leia-meO que é, como jogar, controles, requisitos, equipe, créditos e licençasREADME.md na raiz
RegistroVersão marcada (git tag v1.0.0) e lista de mudançasRelease e histórico do Git
Créditos e licenças. Todo asset de terceiros usado (sons, texturas, modelos, fontes) entra nos créditos com autor, origem e licença. Faça a lista conforme os assets entram no projeto, não na véspera.

Checklist final

  • o jogo abre, joga do começo ao fim e fecha sem erro, em um computador diferente do seu;
  • os controles aparecem na tela inicial ou no README;
  • os testes automáticos passam;
  • o save funciona e resiste a arquivo apagado;
  • o Console da build não mostra erros em vermelho;
  • o repositório não tem senhas, chaves nem pastas geradas;
  • a versão está marcada e os créditos estão completos.

Checkpoint do módulo

  • pelo menos 6 testes automáticos úteis, entre EditMode e PlayMode, todos passando;
  • um relatório de playtest com observações de pessoas de fora da equipe;
  • um print do Profiler com o desempenho medido e uma melhoria feita a partir dele;
  • a build compactada, testada em outro computador;
  • repositório organizado com README, créditos, tag de versão e lista de mudanças.

Problemas comuns

O teste não encontra minhas classes

O assembly de teste não referencia o assembly do jogo. Abra o arquivo .asmdef dos testes e adicione Jogo em Assembly Definition References.

Depois de criar o assembly, aparecem erros de InputSystem

O assembly Jogo não enxerga o pacote do Input System. Adicione Unity.InputSystem às referências dele.

O teste de PlayMode falha só na primeira conferência

Faltou um yield return null depois do AddComponent: o Awake ainda não rodou e os valores estão em zero.

A build abre e fecha ou fica com tela cinza

Confira Scenes in Build e o arquivo Player.log (em AppData\LocalLow, na pasta da empresa e do produto): ele diz qual erro derrubou o jogo.

O repositório ficou gigante

Faltou o .gitignore de Unity e as pastas Library e Temp foram para o Git. Adicione o arquivo, remova as pastas do índice com git rm -r --cached e faça um novo commit.
